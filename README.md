# CampusCare

CampusCare is a Flask/Jinja2 and SQLite maintenance issue desk for college campuses. Students submit and track reports, administrators manage service levels and assignments, and staff record work through resolution. The app includes password recovery, in-app notifications, optional SMTP delivery, deadline alerts, feedback, and an audit timeline.

## Requirements

- Python 3.10+
- Flask, installed from `requirements.txt`

## Run locally (Windows PowerShell)

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
$env:SECRET_KEY = [guid]::NewGuid().ToString("N")
$env:APP_ENV = "development"
python app.py
```

Open `http://127.0.0.1:5000`. The SQLite database and private uploads are stored under `instance\` by default. Keep the same `SECRET_KEY` between restarts so sessions remain valid.

The built-in Flask server is for local development only. Run production behind HTTPS with a production WSGI server and a persistent SQLite volume or a supported production database.

## Environment variables

| Variable | Purpose |
| --- | --- |
| `SECRET_KEY` | Required persistent random signing key; mandatory when `APP_ENV=production`. |
| `APP_ENV` | `development` shows local password-reset links; `production` disables debug mode and enables secure session cookies. |
| `SMTP_HOST` | SMTP server hostname. When omitted in development, email content is logged locally. |
| `SMTP_PORT` | SMTP port; defaults to `587`. |
| `SMTP_USERNAME` / `SMTP_PASSWORD` | Optional SMTP authentication. |
| `SMTP_USE_TLS` | Enable STARTTLS; defaults to `true`. |
| `MAIL_FROM` | Sender header; defaults to a local CampusCare address. |
| `PUBLIC_BASE_URL` | Public HTTPS origin for links generated by scheduled CLI notifications, e.g. `https://care.example.edu`. |
| `INSTANCE_PATH` | Optional persistent Flask instance directory; defaults to the project `instance\` directory. |
| `DATABASE` | Optional SQLite database path; defaults to `instance\campuscare.sqlite3`. |
| `UPLOAD_FOLDER` | Optional private upload directory; defaults to `instance\uploads`. |
| `TRUST_PROXY` | Set to `true` only when a trusted reverse proxy directly fronts the app. |

In production, keep `INSTANCE_PATH`, `DATABASE`, and `UPLOAD_FOLDER` on persistent storage. Staff resolution proof accepts one new photo (JPG, PNG, or WebP, up to 3 MB) and one new video (MP4, WebM, or MOV, up to 50 MB) per resolution update.

## Production deployment (Ubuntu Linux)

The following is a single-server deployment using Gunicorn, systemd, Nginx, HTTPS, and a persistent SQLite/upload directory. CampusCare applies its idempotent schema setup and additive migrations at startup; keep one Gunicorn worker when using SQLite.

1. Install the system packages and create the service/data directories:

   ```sh
   sudo apt update
   sudo apt install -y git python3 python3-venv python3-pip nginx openssl certbot python3-certbot-nginx
   sudo useradd --system --create-home --home-dir /opt/campuscare --shell /usr/sbin/nologin campuscare
   sudo install -d -o campuscare -g campuscare /opt/campuscare/app /var/lib/campuscare/uploads
   ```

2. Deploy the project source to `/opt/campuscare/app` (replace the repository URL and branch):

   ```sh
   sudo -u campuscare git clone --branch main <repository-url> /opt/campuscare/app
   sudo -u campuscare python3 -m venv /opt/campuscare/app/.venv
   sudo -u campuscare /opt/campuscare/app/.venv/bin/pip install --upgrade pip
   sudo -u campuscare /opt/campuscare/app/.venv/bin/pip install -r /opt/campuscare/app/requirements.txt
   ```

3. Generate a signing key and create a root-readable environment file. Replace the SMTP values and hostname:

   ```sh
   openssl rand -hex 32
   sudo install -o root -g root -m 600 /dev/null /etc/campuscare.env
   sudoedit /etc/campuscare.env
   ```

   Set these values in `/etc/campuscare.env`:

   ```text
   APP_ENV=production
   SECRET_KEY=<paste-the-generated-random-value>
   INSTANCE_PATH=/var/lib/campuscare
   DATABASE=/var/lib/campuscare/campuscare.sqlite3
   UPLOAD_FOLDER=/var/lib/campuscare/uploads
   PUBLIC_BASE_URL=https://care.example.edu
   TRUST_PROXY=true
   SMTP_HOST=smtp.example.edu
   SMTP_PORT=587
   SMTP_USERNAME=<mail-account>
   SMTP_PASSWORD=<mail-password>
   SMTP_USE_TLS=true
   MAIL_FROM="CampusCare <noreply@example.edu>"
   ```

   The service user must own `/var/lib/campuscare`; keep the environment file out of the repository and restrict access to it.

4. Create the first administrator. This runs the same production configuration and initializes a fresh database if needed:

   ```sh
   sudo bash -c 'set -a; . /etc/campuscare.env; set +a; cd /opt/campuscare/app; runuser --preserve-environment --user=campuscare -- .venv/bin/flask --app app create-admin'
   ```

5. Create `/etc/systemd/system/campuscare.service`:

   ```ini
   [Unit]
   Description=CampusCare issue desk
   After=network.target

   [Service]
   User=campuscare
   Group=campuscare
   WorkingDirectory=/opt/campuscare/app
   EnvironmentFile=/etc/campuscare.env
   ExecStart=/opt/campuscare/app/.venv/bin/gunicorn --workers 1 --threads 4 --timeout 120 --bind 127.0.0.1:8000 app:app
   Restart=on-failure
   RestartSec=5

   [Install]
   WantedBy=multi-user.target
   ```

   Then enable it:

   ```sh
   sudo systemctl daemon-reload
   sudo systemctl enable --now campuscare
   sudo systemctl status campuscare
   ```

6. Configure Nginx for the domain in `/etc/nginx/sites-available/campuscare`:

   ```nginx
   server {
       listen 80;
       server_name care.example.edu;
       client_max_body_size 54m;

       location / {
           proxy_pass http://127.0.0.1:8000;
           proxy_set_header Host $host;
           proxy_set_header X-Forwarded-Host $host;
           proxy_set_header X-Real-IP $remote_addr;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
           proxy_set_header X-Forwarded-Proto $scheme;
       }
   }
   ```

   Enable Nginx and TLS (point DNS to the server first):

   ```sh
   sudo ln -s /etc/nginx/sites-available/campuscare /etc/nginx/sites-enabled/campuscare
   sudo nginx -t
   sudo systemctl reload nginx
   sudo certbot --nginx -d care.example.edu
   ```

For deployments with mounted disks, mount the persistent disk at `/var/lib/campuscare` and keep the three storage paths above on that disk. Back up the SQLite database and uploads together. For releases, update the source, install `requirements.txt`, then restart `campuscare`; do not delete the persistent data directory. `Procfile` provides the equivalent single-worker Gunicorn start command for Linux PaaS hosts.

## First administrator

Create the database automatically by starting the app, then create the first administrator interactively:

```powershell
flask --app app create-admin
```

Administrators can create staff accounts from the dashboard. Students can self-register and sign in immediately. In development, password-reset links are clickable on the page; in production, they are sent by SMTP.

## Deadlines and notifications

Default service targets are High = 24 hours, Medium = 72 hours, and Low = 168 hours. Administrators can adjust service targets, due-soon windows, and escalation timing in **Settings**. Deadlines are stored in UTC and shown in Asia/Kolkata time.

Run the deadline checker from a scheduler (for example, once per hour):

```powershell
flask --app app check-deadlines
```

The checker creates deduplicated due-soon/overdue notifications and escalates issues that exceed the configured overdue period. It is a command, not a continuously running scheduler; configure Windows Task Scheduler or cron to invoke it regularly.

## Demo walkthrough

In development only, explicitly create sample users and an overdue, due-soon, and on-track issue:

```powershell
flask --app app seed-demo
```

The command prints a random password once for each newly created demo account. Existing demo users are left unchanged. Demo accounts are never created automatically and the command refuses to run when `APP_ENV=production`.

## Database migration

The schema lives in `schema.sql`. Startup applies additive, idempotent migrations for notification preferences, SLA fields, settings, notification storage, indexes, and missing deadlines. The earlier CampusCare database layout is migrated while preserving users, issues, history, and available issue images. Back up the SQLite file before deploying application updates.

## Viva talking points

- **Centralized reporting:** Students file searchable, categorized reports with locations and registered accounts.
- **Role-based workflow:** Admins set priorities, deadlines, and assignments; staff update only their assigned work.
- **SLA handling:** Priority-based UTC deadlines, live urgency states, due-soon/overdue alerts, and one-time escalation.
- **Auditability:** Each status, assignment, resolution remark, and student rating is recorded in issue history.
- **Notifications:** In-app and optional email updates use per-user email preferences and deduplication keys.
- **Data protection:** Password hashing, CSRF checks, role-scoped issue access, private image serving, and safe schema migrations.
- **Operational visibility:** Admin KPIs, Chart.js reports, workload summaries, satisfaction ratings, and CSV export.
